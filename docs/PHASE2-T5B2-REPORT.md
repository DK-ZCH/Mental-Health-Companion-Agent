## 2. 为什么是「限管理员」而不是「删除」——证据驱动

| 证据 | 结论 |
| --- | --- |
| `yonghu/list.vue:738` → `url: "yonghu/resetPassword?id=" + id` | ✅ 管理端**「重置密码」按钮的真实调用方** |
| `xinlilaoshi/list.vue:750` → `url: "xinlilaoshi/resetPassword?id=" + id` | ✅ 同上 |
| 用户端 60 个文件 + 管理端 82 个文件 | ❌ 除此之外**零调用** |

→ 这两个接口是**合法管理功能**，不能删；缺的是**授权**（原先「任一登录学生即可重置他人密码」= 账户接管）。故修法是**限管理员**，保留管理端可用性。

## 3. 关键设计：测试**不产生任何真实数据变更**

要求（你明确提出）：**不得为了验证漏洞而真的把某个用户密码改成 `123456`**。

采用「**前置快照 → 前置校验 → 请求 → 后置比对**」：

```text
① 读取目标密码（快照）
② 【安全闸门】断言种子密码本就是 "123456"   ← 若某天种子数据变了，这里先失败，
                                             从而【避免】后续请求真的改掉密码
③ 发送请求（期望被拒 / 或被允许）
④ 再次读取 → 断言与 ① 完全一致
```

**成功路径（用例 9）**：管理员重置 student 3 / counselor 3 → 因种子密码本就是 `123456`，**数据层幂等** ✓ → 既验证了「管理功能仍可用」，又**零实际变更** ✓。

**独立核验（不依赖测试自身断言）**：在 `mvn test` 前后各查一次数据库：

```text
测试前：s1:123456,s2:123456,s3:123456 | c1:123456,c2:123456,c3:123456
测试后：s1:123456,s2:123456,s3:123456 | c1:123456,c2:123456,c3:123456
结论：✅ 完全一致（测试未改动任何密码）
```

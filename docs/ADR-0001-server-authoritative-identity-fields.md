# ADR-0001：身份属性字段为「服务端权威」

> **状态**：已采纳（2026-10-08）
> **影响范围**：`YonghuEntity` / `XinlilaoshiEntity` 的 `/update` 自助路径（Step 5 批 4-B）
> **决策者**：需求方（Q2 答复）+ 实施方（`idCardNo` 的额外收紧）

---

## 1. 背景

批 4-B 依据需求方答复 **Q2** 实施「自助资料更新」：

> 可自助修改**头像、密码**；老师另可改**个人描述等非固定信息**；
> **学号、工号、学院、性别**_不允许修改_。

## 2. Q2 **明确命名**的字段（证据等级：需求方答复）

| Q2 概念 | 实体字段 | 是否存在 | 能否由 JSON 绑定 | 处置 |
| --- | --- | :-: | :-: | --- |
| 学号 / 工号 | `username` | ✅ | ✅ **可绑定** | **必须**由服务端恢复 |
| 性别 | `gender` | ✅ | ✅ **可绑定** | **必须**由服务端恢复 |
| 学院 | — | ❌ **字段不存在（N/A）** | — | 无需处置 |

## 3. 本 ADR **额外**确立：`idCardNo`（身份证号）同属服务端权威身份属性

⚠️ **性质说明（重要，勿混淆）**：`idCardNo` **不是 Q2 命名的四类字段之一**，
而是**本批额外的安全完整性收紧**。其保留依据是**本 ADR**，不是 Q2。

理由：

1. 它是**身份属性**（与学号/工号同类），业务上不属「用户可自助维护的个人信息」；
2. 事实上 `YonghuEntity.getIdCardNo()` 已标注 `@JsonIgnore`（`YonghuEntity:196`）→
   **本就不从 JSON 绑定** → 服务端恢复属**纵深防御**：防止将来有人摘掉该注解、
   或出现非 JSON 绑定路径时静默失守；
3. 显式恢复让「哪些字段是服务端权威」在代码中**可读、可 grep**，而不依赖注解的副作用。

## 4. 同时澄清的事实（2026-10-08 复核，含对原报告的更正）

| 字段 | `@JsonIgnore` 位置 | 能否由 JSON 绑定 | 复核结论 |
| --- | --- | :-: | --- |
| `password` | `YonghuEntity:156` / `XinlilaoshiEntity:172` | ❌ | `/update` **无法**改密码 |
| `idCardNo` | `YonghuEntity:196` | ❌ | 同上 |

**因此更正原报告的两处表述**：

- ❌ 原述：「任一登录账号可改他人资料，**含 `password`**」→ ✅ 实为：可改他人**可绑定资料字段**（`name` / `phone` / `email` / `avatarUrl` 等）。
- ❌ 原述：「**等于绕开批 2**」→ ✅ **不成立**：批 2 的 `/resetPassword` 是服务端显式 `setPassword("123456")`，与本路径无关；本路径根本改不了密码。

→ 本批闭合的风险应准确定性为 **对象级授权缺失（IDOR / BOLA）**，而非「密码接管」。

## 5. 回退方式（显式、可回滚）

若要允许自助修改身份证号：删除 `YonghuController.update` 中
`yonghu.setIdCardNo(existing.getIdCardNo());` 一行即可，本 ADR 同步失效。

# Agent 执行规则｜Project 2 实现者必读

> **文档性质**：强制行为规范。任何 Agent 在为本项目写代码前，**必须先完整阅读本文件**。
> **优先级**：本文件的约束力 **高于** `PROJECT2-MASTER-PLAN.md` 的路线图。当「完成计划」与「遵守规则」冲突时，**遵守规则**。
> **适用范围**：`d:/ai/job project/Mental Health Companion Agent` 下的一切改造工作。

---

## 0. 一句话总纲

> **不要一次性实现整个 Project 2。**

必须严格遵循：

```text
Step N
  ↓
实现（最小可验证范围）
  ↓
测试
  ↓
展示结果（改动清单 + 测试证据 + 回滚方式）
  ↓
用户确认
  ↓
Step N+1
```

未获得用户确认前，**不得进入下一步**。

## 1. 逐 Step 推进机制（流程规则）

### 1.1 每个 Step 开始前

| # | 动作 | 说明 |
| --- | --- | --- |
| 1 | 确认前置依赖已完成 | 见 `PROJECT2-MASTER-PLAN.md` §7 的 Step 依赖；未完成不得开始 |
| 2 | **核对文档与真实代码** | Master Plan 是路线图，可能与代码不一致；**以代码为准** |
| 3 | 声明本 Step 的范围 | 明确「做什么」与「**不做什么**」 |
| 4 | 确认是否涉及数据库变更 | 若涉及，先出迁移方案（见 §3 规则 2） |

### 1.2 每个 Step 进行中

- 只改动本 Step 声明的文件范围，**禁止顺手重构无关代码**
- 若发现必须扩大范围，**停下并说明原因**，等待用户确认

### 1.3 每个 Step 完成后（必须提交三样证据）

| 证据 | 要求 |
| --- | --- |
| **改动清单** | 逐文件说明改了什么、为什么 |
| **测试结果** | 实际运行结果（命令 + 输出），**不接受「应该没问题」** |
| **回滚方式** | 如何撤销本 Step（分支/git revert/具体步骤） |

> ⚠️ **当前项目尚未纳入 Git 版本控制**（工作区无 `.git`）。因此：
> - 在进入任何会改动 `src/` 的 Phase（Phase 2）之前，**必须先 `git init` 并提交初始基线**，否则「每步可回滚」无法保证；
> - 若用户不同意初始化 Git，则每个 Step 必须改为「改动前备份受影响文件 + 明确手写回滚步骤」。

### 1.4 禁止行为

- ❌ 禁止连续执行多个 Step 后一次性汇报
- ❌ 禁止在未测试的情况下宣称「完成」
- ❌ 禁止跳步（如跳过 Step 0 直接做 Phase 2）

## 2. 六条严禁（硬约束，无例外）

### 严禁 1：不允许为了 Agent 化删除原有业务

```text
先保留旧业务 → 再逐步 Agent 化
```

- 旧功能在改造期间必须仍然可用
- 需要下线某功能时，**必须单独提出并经用户确认**

### 严禁 2：不允许直接修改数据库结构

必须走完整流程：

```text
现有 schema
    ↓
分析影响（哪些代码/流程受影响）
    ↓
迁移方案（DDL + 回滚脚本 + 数据兼容性）
    ↓
用户确认
    ↓
执行
```

- 禁止「顺手加个字段」
- 涉及 16 张既有表（`yonghu` / `xinlilaoshi` / `jiankangzhishi` / `exam*` / `xinlilaoshi_*` / `tongzhi` / `token` / `users` / `config` / `dictionary`）的任何变更，一律先出方案
- **无物理外键**，所有关联均为逻辑关联 → 改动时须自行保证一致性

### 严禁 3：不允许把业务逻辑塞进 Prompt

```text
LLM 决定语义，代码决定合法性
```

| 交给 LLM | 交给代码 |
| --- | --- |
| 理解用户意图 | 参数校验（类型/范围/必填） |
| 自然语言表达 | 权限判断（谁能看/改什么） |
| 解释统计结果 | 数据一致性（事务） |
| 选择调用哪个 Tool | 业务规则（如预约时间是否可用） |

- 禁止用 Prompt 代替 if 判断
- 禁止把「不允许越权」这类规则写成提示词而不写校验代码

### 严禁 4：不允许直接把 Entity 暴露给 LLM

- `com.entity.*` 中的 Entity **禁止**作为 Tool 入参/出参或 LLM 上下文
- 必须建立 **Tool DTO / 领域 DTO**，只暴露必要字段
- 尤其涉及用户隐私字段（`yonghu_id_number`、`yonghu_phone`、邮箱、密码）时，**必须脱敏或剔除**

### 严禁 5：不允许为了「高级」强行增加 Multi-Agent

判断标准：

```text
单 Agent + Tool + RAG 能解决 → 就用单 Agent
```

- 禁止为简历堆砌 Multi-Agent / Workflow / 复杂编排
- 引入任何复杂架构前，必须先证明单 Agent 方案不足，并获用户确认

### 严禁 6：不允许一次修改前后端几十个文件然后说「完成」

- 每个 Step 的改动必须**可回归**
- 单 Step 涉及文件数明显超出预期时，**拆分或先说明**

## 3. 分层与依赖约束

### 3.1 强制分层

```text
Controller
    ↓
Application / Agent
    ↓
Tool
    ↓
Service
    ↓
DAO / Mapper
    ↓
Database
```

### 3.2 禁止的越层调用

```text
❌ Controller → LLM
❌ Controller → 直接 SQL
❌ Tool → 直接 SQL / 直接 DAO 拼条件
❌ Agent → 绕过 Service 访问数据库
```

### 3.3 正确示例

```text
✅ Controller → Agent → Tool → Service → ServiceImpl → Dao → MySQL
✅ Tool 返回值 → Tool DTO → LLM
```

## 4. 身份与权限规则

- **禁止**从用户输入（请求参数 / LLM 生成的参数）判断「当前用户是谁」
- 统一走：

```text
Authentication（拦截器 / Token）
    ↓
CurrentUserProvider
    ↓
currentUserId
```

- 所有用户相关 Tool 必须自动使用服务器端身份：

```text
get_my_health_profile
get_my_assessment
get_my_history
get_my_appointments
```

- 现状：身份来自 `token` 表 + `AuthorizationInterceptor` 写入的 Session（`userId` / `role` / `tableName`）。
  **Phase 2 Step 5 前，任何新增 Tool 都必须显式说明身份来源，不得默认信任入参。**

## 5. 数据与隐私规则

| 规则 | 说明 |
| --- | --- |
| 最小暴露 | 只把完成当前任务所需字段交给 LLM |
| 脱敏 | 身份证号、手机号、邮箱、密码等**禁止**进入 LLM 上下文与日志 |
| 不臆造 | 禁止编造不存在的接口、字段、表、数据 |
| 确定性统计下沉代码 | 平均值/变化率/趋势/次数等**必须由代码计算**，LLM 只解释 |
| 日志脱敏 | 观测日志不得包含明文隐私数据（Phase 11） |

## 6. 安全与产品边界规则（心理健康领域特有）

### 6.1 边界（一切产出必须遵守）

| ✅ 可以 | ❌ 不可以 |
| --- | --- |
| 心理健康知识科普 | 冒充心理医生 / 精神科医生 |
| 帮助理解测评结果与历史变化 | 诊断精神疾病 |
| 一般性自我管理建议 | 依据单次对话判定用户患病 |
| 推荐知识、辅助制定日常计划 | 给出高风险医疗决策 |
| 帮助预约心理老师 | 替代专业心理咨询 |

### 6.2 高风险内容处理（**最严格的一条**）

> **禁止任何 Agent 自行设计「心理危机识别算法」或高风险响应流程。**

正确流程：

```text
发现需要处理高风险场景
    ↓
停止实现
    ↓
产出设计文档（识别标准 + 响应流程 + 话术 + 兜底策略）
    ↓
提交用户确认
    ↓
确认后才可实现
```

- 涉及自伤、自杀、伤害他人等内容的识别与响应，**一律适用本规则**
- 不得把高风险判断仅交给 LLM 自由发挥

### 6.3 Tool 权限分级参考

| 动作 | 等级 | 要求 |
| --- | --- | --- |
| 读取自己的数据 | LOW | 自动使用当前身份 |
| 预约咨询 | MEDIUM | 参数校验 + 身份校验 |
| 取消预约 | MEDIUM–HIGH | 需确认；考虑是否需要用户二次确认 |

> 具体分级在 Phase 9 Step 29 按实际业务最终确定。

## 7. 前端规则

- 前端从 **Step 0** 起就是一等公民，**禁止**「后端做完再随便美化」
- 用户端采用 **Vue 3 SPA**（ADR-002），管理端暂时独立，二者技术栈并存是已知过渡状态
- UI 文案不得使用「诊断 / 治疗 / 医嘱 / 患者」等医疗措辞
- 必须包含：空状态、Loading、Error 三类反馈
- 组件必须来自统一 Design System，**禁止每页自行造轮子**
- AI 助手页面必须对 Tool Calling 过程给出结构化反馈（如「正在查询你的最近一次测评……」）

## 9. 文档与沟通规则

- 本项目的产出语言为**简体中文**
- 汇报必须**条目化**，避免散文式描述
- 引用代码位置时给出**文件路径 + 行号范围**
- 不确定的事实**必须标注「待确认」**，禁止推测性陈述
- 与本文档或 Master Plan 不一致时，**以真实代码为准，并回写文档**

### 9.1 `docs/` 的 Git 边界（**硬规则，禁止违反**）

- **`docs/` 一律不纳入版本控制**：既不上传 GitHub，也不建立本地 Git 追踪；`.gitignore` 必须保持排除 `docs/`
- **原因**：文档中含**明文凭据**（如 `jiaojie.md` 的演示账号）与**未修复漏洞的攻击细节**（水平越权 / 匿名枚举 / 密码重置越权）—— 上传公开仓库等同**漏洞披露 + 凭据泄露**
- **`git push` 属「需明确授权」的操作**：任何 push（尤其 `--force`）都必须先获得用户明确指示，禁止因「这是备份/为你好」而自行发起
- **事故记录**：2026-10-05 曾把 `docs/`（17 份）提交并推送到 GitHub → 已用 `git push --force-with-lease` 重写远程分支历史移除，并用 `reflog expire` + `gc --prune=now` 清除本地对象
- **若需备份文档**：走**离线副本**（打包到私有位置），不要走本仓库的 Git

## 四、设计（v2 冻结）

### 4.1 定位（措辞纪律）

```text
✅ 是什么：一个【确定性出口】—— 命中「明确意图表达」时，
          无论模型说什么，回答里【一定】附带转介资源。

❌ 不是什么：不是风险评估、不是危机筛查、不是诊断；
          尤其【不代表】「未命中 = 用户安全」。
```

> 用户 Q1 裁定的实质：**「宁可误报不可漏报」不能作为放弃上下文的理由**。
> 本设计因此**不接受**「出现关键词即触发」，只接受**意图命中**。

---

### 4.2 L1 规则设计（语义命中，非关键词扫描）

#### 4.2.1 三层判定顺序（**顺序不可调换**）

```text
① 归一化       全角→半角、去多余空白（不改写用户语义，不做拼音/谐音扩展）
      ↓
② R 组：意图命中    只在【第一人称或隐含自身】语境下成立
      ↓
③ N 组：排除项      否定 / 第三人称 / 引用讨论 —— 仅作用于【被它覆盖的那一段】
      ↓
④ 结论          剩余任一条 R 命中 ⇒ trigger = true
                否则 ⇒ trigger = false（且 answer 不得含任何卡片）
```

> **关键**：排除项**按片段（span）作用**，不是全局一票否决。
> 例：「我不想自杀，但我想死」—— 否定只覆盖「自杀」那一段，**「想死」仍触发**。

#### 4.2.2 R 组（命中项，语义族）

| ID | 语义族 | 典型表达（示意，非穷举）|
| :-: | --- | --- |
| R1 | **意愿** | 想 / 要 / 打算 / 准备 / 决定 / 考虑 + 自杀 / 轻生 / 结束自己的生命 / 去死 |
| R2 | **否定生存** | 不想活 / 活不下去 / 活着没意思 / 不如死了 |
| R3 | **进行或计划** | 已经 / 正在 / 马上 / 今晚 / 待会 + 自杀 / 割腕 / 跳楼 / 上吊 / 吞药 |
| R4 | **自伤行为** | 自残 / 自伤 / 割腕 / 划手腕（第一人称语境）|

> R 组**只产出「命中/未命中」**：不做分级、不打风险分、不判断严重程度。

#### 4.2.3 N 组（排除项）

| ID | 语义 | 例 |
| :-: | --- | --- |
| N1 | **否定**：不会 / 没有 / 从未 / 不再 / 不至于 + 自杀·自伤 | 「我**不会**自杀」⇒ 不触发 |
| N2 | **第三人称 / 引用**：朋友 / 同学 / 室友 / 他 / 她 / 网上 / 有人 / 新闻 + 想·说 + 自杀 | 「**我朋友**之前想自杀，但我没有」⇒ 不触发 |
| N3 | **纯讨论**：新闻 / 报道 / 文章 / 电影 + 自杀（无第一人称意图）| 「**网上有人讨论**自杀」⇒ 不触发 |

#### 4.2.4 判定示例（**这张表直接变成测试**）

| # | 输入 | 期望 | 依据 |
| :-: | --- | :-: | --- |
| E1 | 我想自杀 | ✅ 触发 | R1 |
| E2 | 我不想活了 | ✅ 触发 | R2 |
| E3 | 我准备结束自己的生命 | ✅ 触发 | R1 |
| E4 | 我今晚要跳楼 | ✅ 触发 | R3 |
| E5 | **我不会自杀** | ❌ **不触发** | N1（**用户点名要求的反例**）|
| E6 | **我朋友之前想自杀，但我没有** | ❌ **不触发** | N2 + N1（**用户点名要求的反例**）|
| E7 | **网上有人讨论自杀** | ❌ **不触发** | N3（**用户点名要求的反例**）|
| E8 | **我不想自杀，但我想死** | ✅ **触发** | N1 只覆盖「自杀」；「想死」独立命中（**证明排除项不是全局否决**）|
| E9 | 今天很累，压力有点大 | ❌ 不触发 | 无 R 命中 |
| E10 | 我朋友想自杀，我该怎么办 | ⚠️ **待你补裁**（见 §六-Q1b）| 第三人称 + **求助意图** |

#### 4.2.5 已知限制（必须写进文档，不得隐瞒）

```text
① 规则仍可被绕过：拼音、谐音、隐喻、外语、拆分字（如「自 杀」）均可能漏检
② 不做检出率承诺 —— 这是「有兜底」，不是「有检测」
③ E10 若最终选择「不触发」，则【替他人求助】属已知漏报
④ 归一化【刻意不做】谐音/拼音扩展 —— 那会引入不可控的误报与维护负担
```

### 4.3 L3 输出后置（本设计的核心）

```text
模型返回文本（任意内容，含拒答、含「我不会提供任何帮助资源」）
        ↓
服务端【无条件追加】已确认的资源卡片（追加发生在 Controller/编排层，不在 Prompt 内）
        ↓
最终响应 = 模型文本 + 分隔 + 卡片
```

| 做法 | 模型拒答 | 模型被注入 | 可确定性断言 |
| --- | :-: | :-: | :-: |
| 只靠 Prompt | ❌ 可能整段省略 | ❌ 可能被绕过 | 弱（依赖模型随机性）|
| **服务端后置追加** | ✅ 仍在 | ✅ 仍在 | ✅ **强** |

> 与 Round 1/2「身份来自 `ToolContext` 而非模型参数」是**同一条原则**：
> **把不可失败的保证，放在模型够不到的地方。**

---

### 4.4 响应契约

```text
现状：{ code: 0, answer: "..." }
v1  ：{ code: 0, answer: "...\n\n" + 卡片文本, safety: { triggered: true, version: "safety-v1" } }
```

| 决策 | 说明 |
| --- | --- |
| `answer` **必须含卡片** | 保证前端零改动也能看到（F6 已验证可正确分行）|
| 新增 `safety` 字段 | 结构化断言用；前端**可选**消费，不消费也不坏 |
| **不返回 `ruleIds`** | 会教人如何绕过规则；规则 id **只进日志** |
| 未命中时 | `safety.triggered = false`，**`answer` 不得出现任何卡片**（防噪声与误报）|

### 4.5 Q2 · 资源对象与「确认闸门」（**硬阻塞**）

#### 4.5.1 资源必须是独立配置对象，不得写在规则常量里

```text
规则常量（Q3 已批准）       = 何时触发
资源对象（本节的 Q2）        = 触发后给什么 —— 必须独立，且必须经过确认
```

字段（设计级，非代码）：

| 字段 | 含义 | 未确认时 |
| --- | --- | --- |
| `region` | **部署地区契约**（当前项目**不存在**，需你明确）| `null` |
| `emergencyMedical` | 当地紧急医疗：机构名 + 号码 | **不得填任何默认号（含 120 / 110 / 911）** |
| `crisisHotline` | 心理援助热线：名称 + 号码 + 服务时间 | 空 |
| `schoolCenter` | 校内心理中心（**必须实际存在**）| 空 |
| `verifiedBy` / `verifiedAt` / `source` | 确认人、确认日期、来源 | 空 |

#### 4.5.2 两道闸门

```text
闸门 ①（实施闸门 · 进程外）
   资源未确认 ⇒ 【不进入实现】，不写卡片文案，不写测试期望值
   —— 即当前状态

闸门 ②（运行闸门 · 进程内 · fail-closed）
   即便代码已实现：若 region 为空 或 无任一已确认资源
   ⇒ 不追加卡片 + 启动时 WARN（不静默），
     而【不是】回退到「120」或任何猜测地区
```

#### 4.5.3 未确认资源时**唯一允许**的兜底形态

若你希望先上线一个不含号码的版本，卡片只能是**无地区假设的行为指引**：

```text
· 如果你现在有立即的危险，请联系当地的紧急医疗服务，或前往最近的医院急诊
· 尽量【不要独处】，请联系一位你信任的人陪着你
· 你也可以联系学校的心理中心（若学校提供）
```

> **不得**写成「拨打 120」「拨打 110」「拨打 911」——
> 项目当前**没有部署地区契约**，写具体号码就是在替用户假设地区。

## 九、🟡 R3-Q4（运行时新发现 · 需你裁定）

### 9.1 现象

真实 LLM 的输出里**模型自己写了两组号码**：

```text
**全国24小时心理援助热线 12356**，或**希望24热线 400-161-9995**，会有专业人员陪你说话。
```

而这些号码**不在**服务端卡片中，是**模型自由文本**。

### 9.2 为什么必须上报

| 问题 | 说明 |
| --- | --- |
| 绕过了 Q2 闸门 | Q2 的约束只作用于**服务端追加的卡片**；模型文本不受其约束 |
| 「比没有更糟」的风险 | 用户原话：号码错误比没有号码更糟。模型给的号码**未经我们确认**，也不受部署地区约束 |
| 与设计声明不一致的风险 | 若对外声称「平台不提供未经确认的号码」，实际模型仍会给出 ⇒ **声明与事实不符** |

### 9.3 三种处置（需你选）

| 方案 | 做法 | 可验证性 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A 只记录，不改** | 文档明确：**卡片无号码 ≠ 全文无号码**；模型文本不受控 | ✅ 诚实 | 产品声明需相应收紧；用户仍可能拿到未经确认的号码 |
| **B Prompt 约束（软）** | 在 `AgentPrompts` 增一条「不得给出任何具体电话/热线号码」| ❌ **不可确定性验证**（模型可能不听）| 改动极小，但**不能作为保证**，只能降低概率 |
| **C 服务端后置遮蔽（硬）** | 在追加卡片前后，对模型文本做**号码模式识别并遮蔽**（热线/400/手机号等）| ✅ 可断言、可变异 | 可能误伤正常数字（预约时间、分数）；需定义精确模式；属**新增拦截能力**，超出本轮冻结范围 |

### 9.4 ✅ 裁定结果（用户 2026-11-03）：**B**

```text
Round 3 增加一条 Prompt 约束：
「未经平台配置和验证的电话号码 / 热线号码，不得由 Agent 主动提供」
```

**⚠️ 性质声明（必须与实现一起被引用）**：

| 项 | 说明 |
| --- | --- |
| 它是 | **Prompt 层约束**（软约束）|
| 它不是 | **确定性安全边界**；**不得**宣称「模型输出中的号码已被服务端完全禁止」|
| 为什么仍要做 | 当前已选择「第一版无号码版本」，却允许模型自行生成未确认号码，属**产品语义矛盾**；B 成本极低，且能把边界明确告知模型 |
| 落地位置 | `AgentPrompts` 第 11 条（数据边界）|
| 验证方式 | 仅 `J1` **文本存在性**守卫（`Phase4SafetyFallbackTest`），**不证明模型遵守** |

> 因此产品表述必须写成：
> 「**平台提供的资源卡片不含未经核实的号码**；模型自由文本不受服务端强制约束。」
> —— 而不是「平台不会出现任何电话号码」。

## 一、D4 要解决什么（与 M2 的分工）

```text
M2（已完成 4/4 C1 + 1/1 C4）
  → 证明「当前实现【确实消费】了 DataScope 参数」
  → 方法：删掉消费条件 → 行为测试转红

D4（本文档）
  → 解决「【以后】如何尽早发现：声明了参数，但 SQL 没消费」
  → 属【预防机制】，不是再一次取证
```

| 维度 | M2 | D4 |
| --- | :-: | :-: |
| 时间点 | 事后（对已知模块取证）| 事前 / 合入前 / 启动时 |
| 覆盖对象 | 5 个已证明模块 | **全部 19 个调用点 + 未来新增** |
| 输出 | 「这条约束真的生效」 | 「不一致会被拦下」 |

> 🔴 **D4 不能把审计变成 CLOSED 的捷径**：即使 D4 落地，
> `DataScope` 契约是否闭环仍需**对 19 个调用点逐项确认分类**（C1/C2/C3/C4）。
> D4 只是防止**新的**静默丢弃。

## 二、事实基线（本文所有方案都基于这些实测）

### 2.1 `DataScope.apply` 的实际行为

```java
admin      → return（不 put 任何字段）
student    → params.put(studentField, 当前用户 id)
counselor  → params.put(counselorField, 当前用户 id)
其他/null  → deny()（403，fail-closed）
```

⇒ 每次调用**最多声明 1 个范围字段**，字段名由调用方传入（当前恒为 `studentId` / `counselorId`）。

### 2.2 语句结构极其规整（对静态方案有利）

| 事实 | 数值 |
| --- | :-: |
| `DataScope.apply` 调用点 | **19** |
| 涉及 Controller | **12** |
| 每个 Mapper XML 的 `<select>` 数量 | **恰好 1 个**，且**全部叫 `selectListView`** |

⇒ 「Controller 调用点 → Mapper 语句」存在**稳定命名约定**（`XxxDao.selectListView`），
静态映射**可行**，不需要靠猜测。

### 2.3 当前的消费矩阵（这就是 D4 必须面对的"已知例外"）

| 模块 | `params.studentId` | `params.counselorId` | 分类 |
| --- | :-: | :-: | :-: |
| `assessment_record` | ✅ | ✅ | C1 |
| `counseling_appointment` | ✅ | ✅ | C1 |
| `counselor_favorite` | ✅ | ✅ | C1 |
| `counselor_message` | ✅ | ✅ | C1 |
| `student` | ✅ | ✅ | C4（已修复）|
| `assessment_answer` | ✅ | ❌ | **C2**（资源级拒绝兜底）|
| `assessment_wrong_question` | ✅ | ❌ | **C2**（同上）|
| `assessment_paper` | ❌ | ❌ | **C3**（已由可见性批次处理）|
| `assessment_question` | ❌ | ❌ | **C3**（同上）|
| `counselor` | ❌ | ❌ | **C3**（公开目录 + 管理端）|
| `knowledge_article` | ❌ | ❌ | **C3**（模型无该维度）|
| `notification` | ❌ | ❌ | **C3**（全站公告）|

**合计 7 个模块存在"至少一个维度被丢弃"**（C2×2 + C3×5）。

> 🔴 **关键设计约束**：任何 D4 机制**上线第一天就会命中这 7 处**。
> 因此机制必须具备**显式例外登记**能力 ——
> 例外不是「关闭检查」，而是「**把静默丢弃变成书面裁定**」。
> 否则要么机制一上线就红（不可用），要么被改成永远绿（等于没做）。

## 三、四个候选方案

### 方案 A：编译期检查（Annotation Processor / 构建期扫描）

| 项 | 内容 |
| --- | --- |
| 原理 | 构建时扫描 `DataScope.apply(request, params, "studentId", "counselorId")` 的**字面量实参**，与对应 `*Dao.xml` 中 `<if test="params.X ...">` 的引用做比对；不一致则构建失败 |
| 能发现 | ① 新增端点调用了 `apply` 但 XML 未消费；② XML 删了条件但 Controller 仍声明 |
| **发现不了** | ① `<if test="false">` 这类**条件永假**（文本上"引用了"，实际不生效）；② 别名写错（`a.student_id` 写成 `b.student_id`）导致条件无效；③ 拼写扩展（`params.counselorIdX` —— 需 token 精确匹配才不漏）|
| 成本 | **高**：需自写 Maven 插件或独立脚本 + XML DOM 解析 + 与 Java AST 对齐；CI 需接一次 |
| 可靠性 | **中**：取决于解析精度；动态 SQL 场景易误报/漏报 |
| 侵入性 | 无运行时侵入；构建时间 +数秒 |
| 主要风险 | 插件本身成为新的维护负担；解析器与 MyBatis 语义不同步 |

### 方案 B：启动期校验（Fail-fast on startup）

| 项 | 内容 |
| --- | --- |
| 原理 | 应用启动时解析全部 `*Dao.xml`，构建 `statementId → 已消费参数集合`；与一份「声明表」比对，缺失则**启动失败** |
| 能发现 | 同 A（静态不一致），但**带病不上线** |
| **发现不了** | 同 A（条件永假 / 别名错误 / 运行时分支） |
| 成本 | **中**：新增一个启动组件；**但需要维护"声明表"** |
| 可靠性 | **中高** |
| 侵入性 | 生产启动多一次 XML 解析（毫秒级）；一旦解析异常可能导致**启动失败**（需 fail-safe 设计） |
| 🔴 主要缺点 | 「声明表」是**新的手工同步点** —— 它自己会漂移，等于把问题从 XML 搬到配置里 |

### 方案 C：测试期静态一致性测试

| 项 | 内容 |
| --- | --- |
| 原理 | JUnit 测试扫描 `src/main/java/**/controller` 与 `src/main/resources/mapper/*.xml`，断言「每个 `apply` 调用的目标语句必须消费所声明的字段」；**例外清单必须精确匹配** |
| 能发现 | 同 A（静态不一致）+ **例外清单本身被锁住**（谁偷偷放宽，测试立刻红） |
| **发现不了** | 同 A（条件永假 / 别名错误） |
| 成本 | **低**（一个测试类 + 一个白名单常量；无构建插件、无启动组件） |
| 可靠性 | **中高**（token 精确匹配前提下） |
| 侵入性 | **零生产侵入**（只在测试期） |
| 主要风险 | 只在跑测试时发现（若绕过 CI 直接发布则无感） |

### 方案 D：运行期 MyBatis 拦截器（基于真实 `BoundSql`）

| 项 | 内容 |
| --- | --- |
| 原理 | ① `DataScope.apply` 把「本次声明了哪些字段」写入 request attribute；② 拦截 `Executor#query`，读取 `BoundSql.getParameterMappings()` 的 `property` 集合（形如 `params.counselorId`，**只包含真正生效的条件**）；③ 若声明的字段不在集合中 ⇒ 命中「声明未消费」 |
| 能发现 | ① 未消费；② **条件永假**；③ **拼写扩展**（`params.counselorIdX` ⇒ 真实 mapping 是 `params.counselorIdX`，与声明不符 ⇒ 命中）；④ 别名错误导致"看起来消费了"以外的场景 |
| **发现不了** | ① 参数被消费但**语义错误**（如 `a.student_id` 写成 `a.counselor_id` 仍能匹配字段名）；② 不经 `DataScope` 的路径（新增端点直接 `params.put`）|
| 成本 | **低**：一个 `@Component` 拦截器 + 一处 attribute 写入（约 60–100 行） |
| 可靠性 | **最高**（不靠文本猜测，直接看 MyBatis 真实参数映射） |
| 侵入性 | 运行时每次查询遍历一次 mapping（微秒级）；**需选择动作策略**：`LOG` / `WARN` / `THROW` |
| 主要风险 | ① 无 request 上下文（定时任务/异步）需跳过；② 若在生产 `THROW`，可能因未预料的路径**打断业务** |

## 五、推荐方案（分两阶段，不一次做完）

### 阶段 1：方案 C（测试期静态一致性）+ 例外清单 —— **建议先行**

理由：

1. **零生产侵入**，零启动风险，符合本项目「先取证、后改生产」的节奏；
2. 成本最低（一个测试类），能覆盖**历史上真实发生的失败模式**（C2/C3 都是"从未消费"）；
3. **例外清单本身就是审计产物** —— 把 7 处静默丢弃变成 7 条书面登记，
   每条必须写明「为什么可以丢弃」（C2：资源级拒绝兜底 / C3：模型无该维度）。

关键设计点：

```text
· 字段名必须【token 精确匹配】，不能用 contains
  （否则 params.counselorIdX 会被误判为已消费）
· 例外清单必须【精确相等】断言：
    新增例外  → 测试红（必须人工确认并写明理由）
    删除例外  → 测试红（防止"悄悄收紧后又悄悄放宽"）
· 白名单条目需带 reason 字段，与 C2/C3 登记一一对应
```

### 阶段 2：方案 D（运行期拦截器，**仅 test profile 生效**）—— 建议作为补强

理由：

1. 方案 C **发现不了「条件永假」**，而这正是 no-op 最隐蔽的形态；
2. 基于 `BoundSql.getParameterMappings()`，**不依赖文本解析**，可靠性最高；
3. 只在测试 profile `THROW`，生产默认 `LOG`（或关闭）⇒ **不承担打断业务的风险**。

> ⚠️ **落地前置（诚实标注）**：本文尚未在本项目实测
> `BoundSql.getParameterMappings()` 中 `property` 的确切取值（预期形如 `params.counselorId`）。
> 实施阶段 2 前应先做 **10 分钟 spike**：在现有测试里打印一次 `property` 列表确认命名，
> 再据此写拦截器。若不成立（例如被解析成别的形态），阶段 2 的方案需重新评估。

### 不推荐

| 方案 | 理由 |
| --- | --- |
| **A 编译期** | 能力与 C 重叠，但成本高一个量级（自写插件）；收益不成比例 |
| **B 启动期** | 「声明表」是新的手工同步点，会把问题从 XML 漂移成**配置漂移**；且启动失败代价高 |
| 一次性做 C + D + B | 违反本项目「小批次、可回滚」原则 |

> ⚠️ 若后续确有「带病不上线」的强需求，B 可作为**第三阶段**选项，
> 但前提是**不引入手写声明表**（应复用 C 的扫描结果，从 XML 自动生成）。

## 六、验收标准（可反驳 · 落地后必须逐条演示）

| # | 场景 | 期望 |
| :-: | --- | --- |
| V1 | 给 `KnowledgeArticleController` **临时新增**一次 `DataScope.apply(...)`（XML 无消费）| 阶段 1 **测试红**；阶段 2 **拦截器报错** |
| V2 | 把某 XML 的 `params.counselorId` 改成 `params.counselorIdX` | 阶段 1 **红**（token 精确）；阶段 2 **红** |
| V3 | 把某 XML 的 `<if test="params.counselorId != null">` 改成 `<if test="false">` | 阶段 1 **绿**（静态看不出）；阶段 2 **红** ⇒ 证明两阶段互补 |
| V4 | 往例外清单**新增**一条未登记的模块 | 阶段 1 **红**（必须人工确认）|
| V5 | 从例外清单**删除**一条（模拟收紧）| 阶段 1 **红**（要求同步更新，防悄悄放宽）|
| V6 | 全量回归 | **不新增失败**（197/197 保持）|

> V3 是这套方案的核心价值证明：**它把"两阶段为何不能只做一层"变成可执行断言**。

## 七、D4 明确不解决的事

```text
❌ 不解决 C2 / C3 的「是否应当有该维度」—— 那是业务裁定，不是契约问题
❌ 不替代 M2 行为测试（M2 证明"删了会红"，D4 证明"没消费会被提前发现"）
❌ 不检测「参数被消费但语义错误」（如条件用错列）—— 那需要 SQL 语义审计
❌ 不覆盖绕过 DataScope 的路径（新端点自己 params.put）
❌ 不因 D4 落地而关闭 DataScope 审计
```

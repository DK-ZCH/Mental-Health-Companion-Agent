# 面试问答与证据链（Phase 4 收口）

> **基线**：`057c774` · 299 测试 · 21 项变异（R2 4 + R3 5 + R4 8 + Obs 4）
> **用法**：每题的「30 秒版」用于口头回答；「证据」用于被追问时给出可复现事实；
> 「不要这样答」是**必须避开的过度表述**。

---

## Q1 为什么不用 Memory？

**30 秒版**
> 我评估过，但三项前置都不具备：请求体没有 `conversationId`、全库 17 张表没有任何会话/记忆表、
> 前端也没有会话 UI。硬做只能得到「服务端缓存 + 猜测会话」的假多轮，
> 而且 `conversationId` 会成为一个新的客户端可控标识，和「身份只来自服务端」的原则冲突。

**证据**
- `AgentChatRequest` 只有 `message`；`AgentService` 注释明确「不做 ChatMemory」
- 表清单实测：无 `conversation / chat / memory / session`
- Round 4 用的是 `HttpSession` 单条**预约草稿**，不是 Memory（见 Q3）

**如果继续追问**
> 「那你怎么处理需要上下文的两步操作？」→ 只在**业务确有必要**的一处（预约确认）用服务端草稿，
> 且明确它**不是授权依据**，值仍是签名 token，确认时全部重新验签。

**不要这样答**：「我们支持多轮」「用 Session 做了 Memory」。

## Q2 为什么没有 RAG？

**30 秒版**
> 因为语料还不存在。`knowledge_article` 只有 5 条、每条 7 个字符的占位内容。
> 这时候接向量库，只能证明「会调检索接口」，不能证明「答得对」，
> 反而会造出一个看起来高级、实际不可验证的模块。

**证据**
- SQL 实测：`COUNT=5`，`MIN=MAX=AVG=7`
- 盘点文档把它列为「硬阻塞」，不是「以后再说」

**如果继续追问**
> 「怎么才算可以做？」→ 先做知识内容建设（真实文章、可引用的段落），
> 再定义 ground truth 与引用来源，最后才是向量库与切分策略。

**不要这样答**：「有 RAG，只是没接入」「知识库问答已支持」。

## Q3 为什么预约确认不是「多轮 Agent」？

**30 秒版**
> 因为 Agent 本身仍是单轮无状态。我只是把**一次业务编排所需的短期状态**放在 `HttpSession` 里：
> 预览时签一个 token 存进去，确认时服务端把它取出来放进 `ToolContext`。
> 它有三个硬约束：单会话只保留一条（新的覆盖旧的）、确认成功或失败都清理、
> **Session 不是授权依据**（确认仍要验签 + 重新校验）。

**证据**
- `AgentController`：`PENDING_APPOINTMENT_CONFIRMATION` 的写入/清理
- 测试：`Phase4AppointmentSessionFlowTest` C1–C5（跨请求、覆盖、清理、无草稿、跨用户凭证）
- 变异 M8（不清理草稿）⇒ C1/C3/C5 转红

**如果继续追问**
> 「为什么模型会知道有草稿？」→ 无状态模型不知道，所以服务端在**存在草稿**时，
> 向 system prompt 末尾追加一句状态提示（不改用户输入）。
> 实测：只改工具描述模型不调用；加提示后才成功。

**不要这样答**：「实现了多轮会话」「有 Agent Memory」。

## Q4 Tool 参数为什么不进日志？

**30 秒版**
> 因为这是心理健康数据。Tool 的入参和返回值里可能出现分数、留言正文、咨询师信息。
> 观测层只需要回答「调了哪个工具、多久、成功没有」，这三项足够排障与面试追问，
> 但不足以泄露业务内容。

**证据**
- `ToolCallRecorder`：`record(name, durationNanos, success)`，API 上**没有**参数字段
- 日志格式固定：`[AGENT][TOOL] name=... elapsedMs=... ok=...`
- 测试 O5：入参/返回值/异常消息各放哨兵串（`SENSITIVE-IN` / `SECRET-OUT` / `SECRET-EXC`），
  断言日志三者都不含；连 `userId` 也不含
- **变异 M3**（把 `toolInput` 拼进日志）⇒ O5/O6 转红 → 证明这不是口头承诺

**如果继续追问**
> 「排障不够怎么办？」→ 那要单独立项做「脱敏后的结构化日志」，
> 而不是在观测层偷偷扩大字段。

**不要这样答**：「日志里有一些上下文方便排查」（等于承认泄露）。

## Q5 为什么同时需要应用查重和数据库唯一约束？

**30 秒版**
> 两者职责不同：应用层查重负责**业务语义**（给用户「该时段已被预约」的明确提示），
> 数据库唯一约束负责**并发下的最终一致性**。只有应用层，两个并发请求会同时通过；
> 只有数据库，用户只能看到一条冷冰冰的冲突。
> 我的变异实验也验证了这个分工：删掉应用层查重后，串行重复用例转红，
> 但并发兜底的用例仍然通过 —— 因为数据库接住了。

**证据**
- `AppointmentWriteService.existsActiveSlot`（应用层）
- `uk_counselor_slot`（`counselor_id + appointment_date + time_slot + active_slot_guard`）
- 变异 M4（删应用查重）⇒ 仅 S2 红，S4 仍绿
- 变异 M5（临时卸索引）⇒ S18 红

**如果继续追问**
> 「为什么唯一键里有个 `active_slot_guard`？」→ 因为 `status=3`（老师拒绝）不应继续占槽；
> 用生成列 `CASE WHEN status=3 THEN NULL ELSE 1 END`，MySQL 唯一索引允许多个 NULL，
> 于是拒绝后槽位自动释放，且现有数据零冲突。

**不要这样答**：「加了唯一索引就幂等了」（生成列解决的是「拒绝释放」，不是幂等本身）。

## Q6 为什么安全兜底不能只交给 Prompt？

**30 秒版**
> 因为 Prompt 是概率性的。模型可能拒答、可能被注入、可能「忘记」。
> 我把兜底做成**服务端后置追加**：模型回答完之后，服务端再拼上资源卡片，
> 卡片根本不在 Prompt 里，所以模型删不掉。测试里我让模型返回
> 「我不会提供任何帮助资源。」，最终响应仍然含服务端资源。

**证据**
- `AgentService.appendResources`（命中后追加）
- 测试 F3 / `modelCannotSuppressResources`
- 变异 M2（删服务端追加，只靠 Prompt）⇒ 12 条转红
- 变异 M4（信任模型「已给资源」）⇒ 恰好只红 `modelCannotSuppressResources`

**如果继续追问**
> 「那号码呢？」→ 号码只是 **Prompt 软约束**，服务端只保证**卡片**不含未核实号码；
> 模型自由文本仍可能输出号码，这一点我登记为技术债，没有宣称「已被完全禁止」。

**不要这样答**：「Prompt 里写了所以模型不会说」。

## Q7 299 个测试究竟证明了什么，又没有证明什么？

**30 秒版**
> 它证明的是**确定性边界**：身份域、工具字段白名单、状态转换、查重与唯一约束、安全兜底、
> 观测不改行为 —— 而且 21 项变异让这些断言可被证伪。
> 它**没有**证明「Agent 全链路都经过真实运行验证」：真实 LLM 只覆盖了部分工具，
> T0/T3/T4 仍是测试级验证；也没有性能、并发压测和真实用户验证。

**证据**
- 盘点文档 `PHASE4-CAPABILITY-INVENTORY.md` 的**三级证据口径**（L1 测试 / L2 变异 / L3 真实运行）
- 每个能力的 L3 列：T1/T2/T5/T6/T7 与安全兜底有真实运行；T0/T3/T4 标注「未单独验证」

**如果继续追问**
> 「那你怎么保证 T0/T3/T4 能用？」→ 有集成测试断言其返回与数据库 oracle 一致；
> 如果要提升到 L3，补真实 LLM 抽查即可，成本很低。

**不要这样答**：「299 个测试覆盖了全链路」。

## Q8 你怎么知道模型调了哪个工具、调对了没有？

**30 秒版**
> 我统一包装了 `ToolCallback`，在调用前后记录 `toolName / durationMs / success`，
> 且刻意不记录参数与返回。真实运行日志长这样：
> `[AGENT][TOOL] name=getMyAppointments elapsedMs=92 ok=true`。
> 另外这个包装层是旁路的：Recorder 自己出错不影响业务，但工具异常必须原样抛出。

**证据**
- `TimedToolCallback`（成功原样返回、失败原样抛出、Recorder 异常 fail-silent）
- `Phase4ToolObservabilityTest` O1–O7；变异 M1–M4
- Spike 事实：Spring AI 1.1.8 的 `.tools()` **不接受** `ToolCallback`，必须 `.toolCallbacks()`

**如果继续追问**
> 「为什么不记参数？」→ 见 Q4。

## Q9 身份域为什么用 `(userId, userTable)` 二元组？

**30 秒版**
> 因为 id 是**命名空间未限定**的整数：学生 1 和咨询师 1 是两个人。
> 只传 id，Tool 无法区分，这正是我实测到的一次跨角色串读。
> 二元组 + 白名单 + fail-closed 之后，咨询师/管理员在**调用模型之前**就被拒绝。

**证据**
- `AgentIdentity`（`CTX_USER_ID` / `CTX_USER_TABLE`；`toString` 不打印 userId）
- `AgentToolGuard.requireStudent`
- 变异/用例：counselor/admin 403 且 `AgentModel` 调用次数为 0

## Q10 你的 token 为什么不是一次性的？

**30 秒版**
> 因为签名是无状态的：服务端能验「没被改、没过期、是我的、是这个操作」，
> 但**不知道它有没有被用过**。所以重复提交不是靠 token 拒绝，
> 而是靠业务查重 + 数据库唯一键拒绝。这一点我在文档和代码注释里都写死了。

**证据**
- `AppointmentConfirmToken` 注释与 `verify` 六步校验
- 测试 S4（串行重复）/ S18（DB 兜底）
- 变异 M1–M3（删签名/删用户绑定/删过期）分别使对应用例转红

## Q11 为什么加唯一索引之前要先修 `status`？

**30 秒版**
> 因为当时 `/add`、`/save`、`/update` 从不设置 `status`，学生可以 `POST status=2` 自我审批。
> 如果先加唯一索引，这条缺陷会升级成「一次伪造就长期占住槽位」。
> 所以我先做状态来源与转换：创建强制 `1`，更新只允许 `1→2 / 1→3`，
> 并保留咨询师合法的审核路径。

**证据**
- `AppointmentStatusPolicy`
- 测试 S15a/S15b（创建不能伪造）、S16a/S16b（合法审核保留）、S16c（非法跳转 403）、S17（学生改状态被忽略）
- 变异 M6/M7 分别使「创建伪造」与「任意跳转」转红

**不要这样答**：「顺手修了个 bug」——它是启用约束的**前置条件**。

## Q12 如果让你继续做，你会做什么？

**30 秒版**
> 我不会继续加 Tool 数量。优先级是：
> ① 把 `DEBT-AGENT-APPOINTMENT-CONFIRM-RETRY` 收敛成「进入终态才清草稿」；
> ② 如果要做 Memory，先做会话归属设计（conversationId + 存储 + 前端），而不是先做 Agent 记忆；
> ③ RAG 先做内容建设；④ 再评估是否需要一个受控的第二类写操作。
> 每一步都先设计、再冻结验收，不凭「还缺什么」拍板。

**证据**
- 盘点文档 §四 的候选对照（前置、成本、可验证性）
- 两条已挂账债务：`DEBT-AGENT-UNVERIFIED-PHONE`、`DEBT-AGENT-APPOINTMENT-CONFIRM-RETRY`

## 附：被问「这个项目最难的地方是什么」时

> 不是写 Tool，是**划清边界**：
> 哪些保证必须是确定性的（身份、状态、唯一约束、安全兜底），
> 哪些只能做到概率性（Prompt 约束、模型是否愿意调用工具），
> 以及**不把后者说成前者**。这个项目里我为此改了两次设计、加了 21 项变异来证明边界是真的。

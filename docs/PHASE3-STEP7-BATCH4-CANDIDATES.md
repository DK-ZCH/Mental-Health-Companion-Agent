## 3. 🔴 关于 403 的**结构性结论**（本轮审计新认知，重要 ⚠️）

**事实**：403 只在「**已登录但无权**」时产生 —— 即 **ownership 越权**（改/删/读他人）或 **admin-only**。

**推论**：**正确实现的 UI 永远不会主动发出这类请求** ✗。
⇒ **403 的"自然业务 UI 触发"在架构上几乎不可能出现** ⚠️ —— 即使做到 R11–R13 也大概率仍然没有 ✗。

**因此 403 只有三种可能的验证途径**：

| 途径 | 性质 | 是否允许 |
| --- | --- | --- |
| Ⓐ 真实业务 UI 自然触发 | 最理想 | ❌ 结构上几乎不出现 |
| Ⓑ **浏览器上下文负向探针**（用应用自身 axios 发一次越权请求）| 真实运行时 ✓ 但**不是业务流** | ⚠️ 需你裁定（非"造页面"✓，但需暴露 http 实例或临时脚本 ✗）|
| Ⓒ 静态 + API 层双证（现状）| 已具备 ✓ | ✅ 当前口径 |

> **建议**：把 403 从"Batch 必验项"调整为**长期挂账（结构性不可自然触发）** ✓，
> 或明确批准 **Ⓑ 一次性负向探针**（不落业务代码、不提交 ✓）。

## 二、证据（表结构与语义）

### 2.1 `counseling_appointment`

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `appointment_date` | `date` | 预约**日期**（无时刻）|
| `time_slot` | `int`（可空）| 字典 `time_slot`：**1–8，每项固定 1 小时**（08:00–09:00 … 17:00–18:00）|
| `status` | `int`（可空）| 字典 `appointment_status`：**1 待审核 / 2 同意 / 3 拒绝** |
| `appointment_no` | `varchar(200)` | `/add` 用 `System.currentTimeMillis()` 生成 |
| 索引 | — | **仅 `PRIMARY(id)`，无任何唯一索引** |
| MySQL | `8.0.23` | 支持**生成列 + 唯一索引**（含虚拟列二级索引）|

> ⚠️ 字典里**没有「已取消」**：取消 = **物理删除**（`/delete`）。`status=3` 是**老师拒绝**，不是取消。

### 2.3 重复性分组实测

| 维度 | 结果 |
| --- | --- |
| `(counselor_id, date, slot)` | ✅ **无重复** |

| 端点 | 行为 |
| --- | --- |
| `POST /add`（前端使用）| ✅ `studentId` 强制取自 Session · `appointmentNo` 服务端生成 · **不设 `status`** · 仅校验「咨询师存在」· **无日期/时段/重复/冲突校验** |

| `POST /update` | ✅ 归属校验；但 `status` **仍取自客户端实体** |

## 三、时间模型判定（回答你的区间问题）

```text
time_slot ∈ {1..8}，每项是字典里【固定 1 小时】的区间，且互不重叠
⇒ 任意两条预约的时间重叠  ⟺  (appointment_date, time_slot) 完全相同
⇒ 不需要区间 overlap 计算；普通唯一索引即可覆盖「重叠」
```

**成立前提（必须写进实现）**：

```text
Agent 路径必须校验 time_slot ∈ 字典（1..8）
—— 否则可写入 slot=999/0，模型退化，唯一的「等值」假设被破坏
```

**条件失效**：若未来支持「自定义起止时间」，本节结论作废，需改为区间重叠校验 + 数据库层无法兜底（登记为条件，不属本轮）。

## 四、唯一键候选（据证据筛选）

### 方案 A · `UNIQUE(counselor_id, appointment_date, time_slot)`

| 项 | 结论 |
| --- | --- |
| 与现有数据兼容 | ✅ |
| 防「同老师同槽两人」 | ✅ |
| **拒绝后释放槽位** | ❌ **不释放**：`status=3` 的行仍占用，学生无法重约同槽 |

### 方案 B · 唯一键 + 生成列（推荐）

```sql
ALTER TABLE counseling_appointment
  ADD COLUMN active_slot_guard TINYINT
      GENERATED ALWAYS AS (CASE WHEN status = 3 THEN NULL ELSE 1 END) STORED,
  ADD UNIQUE KEY uk_counselor_slot
      (counselor_id, appointment_date, time_slot, active_slot_guard);
```

| 项 | 结论 |
| --- | --- |
| 与现有数据兼容 | ✅（无重复）|
| 防同老师同槽两人 | ✅（`status` 为 1/2/NULL 时守卫为 1）|
| **拒绝后释放槽位** | ✅（`status=3` ⇒ 守卫 `NULL`；MySQL 唯一索引**允许多个 NULL**）|
| 物理删除 | ✅ 行消失，自动释放 |
| 依赖 | MySQL 8.0.23 ✅ 支持 |

### 方案 C · `UNIQUE(student_id, appointment_date, time_slot)`

| 项 | 结论 |
| --- | --- |
| 与现有数据兼容 | 🔴 **不兼容**（student 1 同日同槽 2 条）|
| 业务含义 | 禁止「同一学生同槽约两位老师」——**现有数据证明系统一直允许** |
| 结论 | ❌ **不可加**；若要禁，必须先清理历史数据并改产品语义（独立议题）|

> **不建议**把学生维度与咨询师维度混在一个唯一键里：
> `UNIQUE(counselor_id, student_id, date, slot)` 只能防「同一对师生重复」，**防不住**「同老师同槽两个学生」。

## 五、🔴 前置依赖：`status` 完整性（这是 Q3 的真正风险）

```text
当前：/add 与 /update 从不 setStatus（唯一一处 setStatus 是注释）
⇒ 学生可 POST status=2 → 预约【直接变成已同意】
⇒ 若此时再加「咨询师唯一键」：一次伪造即可【长期占住该槽】，其他学生再也约不上
⇒ 唯一索引把 P1「自审批」升级成「占槽」手段
```

| 选项 | 做法 | 影响 | 建议 |
| --- | --- | :-: | :-: |
| **a. 最小修复** | `/add` 对学生**强制** `status=1`；`/update` 禁止非审核角色改 `status` | 1–2 行代码；顺带修 `SEC-APPOINTMENT-STATUS-SPOOF` 的主体 | ✅ **推荐** |
| b. 不加唯一索引 | 仅应用层查重 | 保留并发窗口；不动 status | 备选 |
| c. 加索引但接受风险 | — | 自审批 ⇒ 占槽 | ❌ 不推荐 |

> **诚实说明**：选 a 意味着**范围扩张**（触及既有端点行为）。
> 但它不是「顺手修 bug」，而是**唯一索引能被安全启用的前提** ——
> 不加 a 而加索引，等于**用一个新约束放大一个既有缺陷**。

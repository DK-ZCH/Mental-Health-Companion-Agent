# Step 0 规范｜旧系统技术审计（只读）

> **Step 编号**：Phase 0 / Step 0（Project 2 的第一个执行步骤）
> **性质**：**只读审计**。产出文档，不改代码。
> **目的**：建立旧项目基线，为后续所有 Phase 提供可信事实来源。
> **前置**：无。本 Step 是整条路线的起点。

---

## 1. 最高优先级禁令（违反即本 Step 失败）

> ### ⛔ 在执行 Step 0 期间，禁止修改任何代码、配置或数据库。

具体禁止清单：

| 禁止项 | 说明 |
| --- | --- |
| ❌ 修改 `src/` 下任何文件 | 含 Java、Vue、HTML、JS、CSS、XML |
| ❌ 修改 `pom.xml` | 不升级、不新增、不删除依赖 |
| ❌ 修改 `src/main/resources/application.yml` | 不改端口、数据源、MyBatis-Plus 配置 |
| ❌ 修改 `mental_health_companion_agent.sql` / 执行任何 DDL / DML | 不改表结构、不插入数据 |
| ❌ 执行 `mvn clean` / `mvn package` 后提交 | 允许为验证启动而构建，但**不得修改源码** |
| ❌ 删除「无用」文件（如 `pages/chat/`、`MyThreadMethod`） | 审计阶段只记录，不清理 |
| ❌ 重构、重命名、格式化 | 一律留到 Phase 2/3 |

> 允许的操作只有：**读取、检索、构建、启动、访问页面、记录结论**。

**理由**：在没有基线之前做任何改动，都将失去「旧系统原本是什么样」的判断依据，后续无法证明「旧业务未被破坏」。

---

## 2. 审计目标

回答以下问题，并留下可追溯证据：

1. 旧系统**当前到底能不能跑起来**？跑通需要什么条件？
2. 旧系统**实际有哪些能力**？（按代码，而非按文档或想象）
3. 旧系统前后端**如何通信**？身份如何传递？
4. 哪些代码**值得保留**、哪些**需要重构**、哪些**不应改动**？
5. 后续 Phase 的路线图需要基于真实情况**如何校准**？

### 5.2 允许的例外

若第 1 项（启动）因环境限制（如无法安装 MySQL、JDK 版本不匹配）无法完成，则：

- **不得**通过改代码来「让它跑起来」
- 必须**详细记录阻塞原因**与已尝试的排查步骤
- 由用户决定是否调整环境或豁免该验收项

> 未经用户同意，**不得以「改代码」方式绕过环境问题**。
